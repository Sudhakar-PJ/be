## Step 0: Architecture Decisions & Token Genesis (Before Any Components)

Before writing or styling any component, two prerequisites must be satisfied:

### Step 0.1: Architecture Decisions (Framework, Tailwind Engine & Design System Theme)
Do not bury framework or design assumptions in component skills. Three foundational architectural choices must be evaluated and documented in `docs/architecture/ADR-001-frontend-framework.md`:
1. **Frontend Runtime:** **Vite + React SPA** vs. **Next.js App Router** (evaluated based on WebSocket connection longevity, client-side table rendering latency, and offline caching).
2. **Tailwind Engine Version:**
   - **Tailwind v4 (Standard for current `npx shadcn@latest init`):** Zero config file (no `tailwind.config.ts`), tokens declared directly in `globals.css` via `@theme inline`, and values expressed in modern CSS color spaces (`oklch(...)`).
   - **Tailwind v3 (Legacy shadcn):** HSL number triplets in `globals.css` mapped through `tailwind.config.ts`.
3. **Design System & Theme Selection:**
   - Choose a baseline aesthetic from [`design-systems`](../design-systems/SKILL.md) (e.g. `enterprise`, `shadcn`, `bento`, `minimal`) or [`impeccable`](../impeccable/SKILL.md).
   - **Explicit Division of Roles:**
     - **Structural colors** (`--background`, `--foreground`, `--card`, `--primary`, `--secondary`, `--accent`, `--popover`, `--border`, `--input`, `--ring`) are dictated by the chosen theme.
     - **Status tokens** (`--destructive`, `--success`, `--warning`, and their subtle/text pill variants) are **mandatory additions** applied on top of any theme.
     - **Contrast Quality Gate:** Any chosen theme's structural foreground/background pairs—including ensuring `--muted-foreground` reaches ≥ 4.5:1 against that theme's `--muted`—must be verified before acceptance. (The `--muted-foreground` value given below is the verified fix for shadcn neutral/zinc; warm or custom themes must be tuned to achieve ≥ 4.5:1 against their respective surface).

### Step 0.2: Design System & Semantic Token Genesis (WCAG 2.1 AA Compliant)
Because `frontend/` starts empty, tokens must be established before UI code is written. Standard `shadcn` defaults carry two accessibility gaps:
- No semantic status tokens for task lifecycles (`success`, `warning`).
- Standard shadcn neutral/zinc `--muted-foreground` (`240 3.8% 46.1%`) on `--muted` produces a **4.39:1** contrast ratio, just failing the 4.5:1 AA gate for small text in table headers and chips. Darkening to `240 4% 42%` (or `oklch(0.517 0.012 286.0)`) delivers **5.10:1**, clearing the gate. If a tinted or warm theme from `design-systems` is chosen, `--muted-foreground` must be tuned to reach ≥ 4.5:1 against that specific theme's `--muted`.

> **Important (Merge, Do Not Overwrite):** The code blocks below are **additions and overrides** to merge into the `globals.css` generated by `npx shadcn@latest init`. Do NOT replace the generated file wholesale. shadcn components depend on `--popover`, `--secondary`, `--accent`, `--input`, and `--ring` for dropdowns, form controls, and keyboard focus rings.

To guarantee Precedence 5 compliance, two tiers of tokens are defined:
1. **Solid Alert Tokens:** High-contrast solid backgrounds with white or dark text.
2. **Subtle Pill Tokens (Linear/Radix standard):** Dedicated muted backgrounds and dark/bright text pairings for table status badges and Kanban issue pills.

#### Format Option A: Tailwind v4 (`globals.css` with `@theme inline` & OKLCH)
Merge these definitions into the generated `globals.css` (the `@import "tailwindcss";` line is already present):
```css

  /* Status Token Mappings */
  --color-destructive: var(--destructive);
  --color-destructive-foreground: var(--destructive-foreground);
  --color-success: var(--success);
  --color-success-foreground: var(--success-foreground);
  --color-warning: var(--warning);
  --color-warning-foreground: var(--warning-foreground);

  --color-success-subtle: var(--success-subtle);
  --color-success-text: var(--success-text);
  --color-warning-subtle: var(--warning-subtle);
  --color-warning-text: var(--warning-text);
  --color-destructive-subtle: var(--destructive-subtle);
  --color-destructive-text: var(--destructive-text);
}

:root {
  /* Override shadcn neutral/zinc muted-foreground to clear WCAG AA 4.5:1 gate (retune for warm/tinted themes) */
  --muted-foreground: oklch(0.517 0.012 286.0); /* Contrast: 5.10:1 on muted */

  /* Solid status tokens (All pass WCAG AA >= 5.3:1) */
  --destructive: oklch(0.509 0.193 27.6);
  --destructive-foreground: oklch(1 0 0);
  --success: oklch(0.512 0.134 149.9);
  --success-foreground: oklch(1 0 0);
  --warning: oklch(0.77 0.165 70.7);
  --warning-foreground: oklch(0.284 0.063 54.7); /* Contrast: 6.87:1 */

  /* Subtle status pill tokens (All pass WCAG AA >= 7.9:1) */
  --success-subtle: oklch(0.978 0.019 157.9);
  --success-text: oklch(0.411 0.107 150.1);      /* Contrast: 7.91:1 */
  --warning-subtle: oklch(0.979 0.024 91.6);
  --warning-text: oklch(0.367 0.087 54.7);        /* Contrast: 10.23:1 */
  --destructive-subtle: oklch(0.968 0.014 17.4);
  --destructive-text: oklch(0.424 0.163 27.9);    /* Contrast: 8.21:1 */
}

.dark {
  /* Solid status tokens */
  --destructive: oklch(0.509 0.193 27.6);
  --destructive-foreground: oklch(1 0 0);
  --success: oklch(0.512 0.134 149.9);
  --success-foreground: oklch(1 0 0);
  --warning: oklch(0.77 0.165 70.7);
  --warning-foreground: oklch(0.284 0.063 54.7);

  /* Subtle status pill tokens (All pass WCAG AA >= 5.8:1) */
  --success-subtle: oklch(0.251 0.053 152.3);
```

#### Format Option B: Tailwind v3 (`globals.css` with HSL triplets & `tailwind.config.ts`)

**1. Merge into `globals.css`:**
```css
:root {
  /* Override shadcn neutral/zinc muted-foreground to clear WCAG AA 4.5:1 gate (retune for warm/tinted themes) */
  --muted-foreground: 240 4% 42%;              /* Contrast: 5.10:1 (clears 4.5:1 AA gate) */

  /* Solid Status Tokens (All pass WCAG AA >= 5.3:1) */
  --destructive: 0 75% 42%;
  --destructive-foreground: 0 0% 100%;         /* Contrast: 6.39:1 */
  --success: 142 72% 28%;
  --success-foreground: 0 0% 100%;             /* Contrast: 5.35:1 */
  --warning: 38 92% 50%;
  --warning-foreground: 26 83% 14%;            /* Contrast: 6.87:1 (dark text on amber) */

  /* Subtle Status Pill Tokens (Linear/Radix Pattern, All pass WCAG AA >= 7.9:1) */
  --success-subtle: 142 70% 96%;
  --success-text: 142 76% 20%;                 /* Contrast: 7.91:1 */
  --warning-subtle: 45 95% 95%;
  --warning-text: 28 90% 20%;                  /* Contrast: 10.23:1 */
  --destructive-subtle: 0 85% 97%;
  --destructive-text: 0 80% 32%;               /* Contrast: 8.21:1 */
}

.dark {
  /* Solid Status Tokens (All pass WCAG AA >= 5.3:1) */
  --destructive: 0 75% 42%;
  --destructive-foreground: 0 0% 100%;         /* Contrast: 6.39:1 */
  --success: 142 72% 28%;
  --success-foreground: 0 0% 100%;             /* Contrast: 5.35:1 */
  --warning: 38 92% 50%;
  --warning-foreground: 26 83% 14%;            /* Contrast: 6.87:1 */

  /* Subtle Status Pill Tokens (All pass WCAG AA >= 5.8:1) */
  --success-subtle: 142 60% 10%;
  --success-text: 142 70% 60%;                 /* Contrast: 9.22:1 */
  --warning-subtle: 38 80% 11%;
  --warning-text: 45 95% 60%;                  /* Contrast: 9.86:1 */
  --destructive-subtle: 0 75% 12%;
  --destructive-text: 0 85% 68%;               /* Contrast: 5.85:1 */
}
```

**2. Add to `tailwind.config.ts` under `theme.extend.colors`:**
Add `success` and `warning`, and **replace the existing `destructive` entry** (to add subtle and text pill support while avoiding TS1117 duplicate key errors):
```ts
// tailwind.config.ts
export default {
  theme: {
    extend: {
      colors: {
        // ... existing shadcn colors (background, foreground, card, primary, secondary, muted, accent, popover, border, input, ring)
        success: {
          DEFAULT: 'hsl(var(--success))',
          foreground: 'hsl(var(--success-foreground))',
          subtle: 'hsl(var(--success-subtle))',
          text: 'hsl(var(--success-text))',
        },
        warning: {
          DEFAULT: 'hsl(var(--warning))',
          foreground: 'hsl(var(--warning-foreground))',
          subtle: 'hsl(var(--warning-subtle))',
          text: 'hsl(var(--warning-text))',
        },
        // Replace existing destructive entry:
        destructive: {
          DEFAULT: 'hsl(var(--destructive))',
          foreground: 'hsl(var(--destructive-foreground))',
          subtle: 'hsl(var(--destructive-subtle))',
          text: 'hsl(var(--destructive-text))',
        },
      },
    },
  },
};
```
All components must consume these semantic tokens:
- **Solid alerts / actions:** `bg-destructive text-destructive-foreground`, `bg-success text-success-foreground`, `bg-warning text-warning-foreground`.
- **Status badges / pills:** `bg-success-subtle text-success-text`, `bg-warning-subtle text-warning-text`, `bg-destructive-subtle text-destructive-text`.
Raw color utilities (e.g. `zinc-950`, `emerald-400`, `amber-500`) are banned in product code.

## 1. The Context Split: Marketing vs. Product UI

Every frontend task MUST be categorized into one of two distinct paradigms:

```
                          [ INBOUND FRONTEND TASK ]
                                      │
                 ┌────────────────────┴────────────────────┐
                 ▼                                         ▼
   [ PARADIGM A: MARKETING UI ]               [ PARADIGM B: PRODUCT UI ]
   • Landing Pages                            • Jira/Linear Task Boards & Sprints
   • Marketing Heroes & Feature Highlights    • Dense Data Tables & Backlogs
   • Pricing & Case Studies                   • Filter Toolbars, Modals & Drawers
   • Visual Storytelling                      • User Settings & Form Workflows
                 │                                         │
                 ▼                                         ▼
   [ SPECIALIZED ROUTING ]                    [ SPECIALIZED ROUTING ]
   • tasteskill v2.5.1                        • impeccable (Paul Bakaus Product UI)
   • motionsites-web-builder                  • shadcn (Radix Accessibility)
   • GSAP / Three.js 3D (where appropriate)   • 21st-cli-use / 21st-ui-explore (Sourcing)
                                              • gestures / animate (Kanban Drag & Drop)
                                              • ask-sonner (Toast Receipts & Undo)
                                              • break-ui (Adversarial Data Stress Test)
```

### Paradigm A: Marketing & Landing Pages
- **Goal:** Visual impact, brand storytelling, conversion.
- **Rules:** Generous whitespace, dramatic typography scales, fluid section transitions, hero entrances.
- **Primary Skills:** [`design-taste-frontend`](../design-taste-frontend/SKILL.md) (`tasteskill v2.5.1`), [`motionsites-web-builder`](../motionsites-web-builder/SKILL.md).

### Paradigm B: B2B Product UI (The Core SaaS Stack)
- **Goal:** Information density, keyboard navigation, zero cognitive friction, data legibility.
- **Rules:** Compact row heights (36px–40px), sticky table headers, optical hover states, high-contrast status pills, <200 LOC component composition.
- **Primary Skills:**
  - **Structure & Critique:** [`impeccable`](../impeccable/SKILL.md) (Paul Bakaus).
  - **Primes & Accessibility:** [`shadcn`](../shadcn/SKILL.md) (Radix primitives).
  - **Component Sourcing:** [`21st-cli-use`](../21st-cli-use/SKILL.md) (search/install CLI) & [`21st-ui-explore`](../21st-ui-explore/SKILL.md) (visual direction sourcing).
  - **Board Drag & Drop:** [`gestures`](../gestures/SKILL.md), [`animate`](../animate/SKILL.md), [`choreograph`](../choreograph/SKILL.md).

## 2. Precedence Hierarchy (Resolving Conflicts)

When skills disagree, this precedence hierarchy is binding:

1. **Precedence 1 (Project Design Tokens Win):** The project's active semantic CSS variables (`bg-background`, `border-border`, `text-success`, `text-foreground`) always override any individual skill's hardcoded palette suggestions.
2. **Precedence 2 (Product UI Dominance):** For app screens (boards, tables, dialogs), `impeccable` and `shadcn` guidelines dominate marketing taste guidelines. Never add decorative parallax or large hero whitespace inside an issue tracker.
3. **Precedence 3 (Motion Restraint in Product UI):**
   - In Product UI: Use lightweight CSS transitions or `emil-design-eng` layout springs (150ms–250ms). Never load heavy GSAP timelines for task card moves or dropdown menus.
   - In Marketing UI: GSAP and ScrollTrigger are permitted for cinematic landing page sequences.
4. **Precedence 4 (Performance Quality Gate):** [`vercel-react-best-practices`](../vercel-react-best-practices/SKILL.md) has final veto power on all component code. If the Step 0.1 ADR selects **Vite + React SPA**, this veto applies strictly to the client-side tiers (`async-*`, `bundle-*`, `rerender-*`, `client-*`, `js-*`, `rendering-*`), ignoring Next.js server-only tiers (`server-*`).
5. **Precedence 5 (Accessibility Gate):** [`web-design-guidelines`](../web-design-guidelines/SKILL.md) enforces non-negotiable WCAG 2.1 AA compliance (keyboard focus rings, screen reader labels, aria attributes).
